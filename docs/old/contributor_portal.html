Backend implementation guide for HRL

HRL is a fully graphics‑API‑agnostic rendering library.
All GPU logic lives exclusively inside the backend through a strict RHI contract. The HRL core never includes or exposes native APIs such as OpenGL, Vulkan, DirectX or Metal. The currently maintained backend targets OpenGL 3.3 Core Profile.

As a backend contributor, you are expected to implement every RHI function. Missing or partially implemented functions result in an invalid backend that will either crash at runtime or silently corrupt GPU state.

⚠️ The backend is solely responsible for resource lifetime, GPU state machines, pipeline objects, framebuffer management and draw-call synchronization. The HRL core makes no assumptions about the underlying API and will never attempt to recover from a missing or broken RHI implementation.

Compile HRL COMPILATION

HRL uses CMake as its build system and is officially supported with MinGW-w64 (GCC for Windows) as the compiler toolchain. Building with another compiler (MSVC, Clang, etc.) is not tested and may introduce undefined behaviour due to ABI differences, non-standard pragma handling and DLL export semantics that the build is specifically tuned for.

⚠️ Compiling HRL with a toolchain other than MinGW-w64 is unsupported. Subtle UB, ODR violations and GPU state corruption may occur silently at runtime. In particular, mixing MSVC-compiled and MinGW-compiled translation units across DLL boundaries is undefined behaviour in C++.

1 — Install MinGW-w64

The recommended distribution is WinLibs, which ships a clean, standalone MinGW-w64 bundle with no installer side effects.

StepAction
Download Go to winlibs.com and download the latest UCRT, POSIX release (choose the x86_64 zip).
Extract Extract the archive to a stable path, e.g. C:\mingw64. Avoid paths with spaces.
PATH Add C:\mingw64\bin to your system PATH via System Properties → Environment Variables → Path → Edit.
Verify Open a new terminal and run gcc --version. You should see a GCC 13+ line referencing MinGW-w64.

2 — Install CMake

Download the latest CMake Windows installer from cmake.org/download. During installation, select "Add CMake to the system PATH for all users". Verify with cmake --version (3.22+ required).

3 — Generate the CMake project

Before compiling for the first time — or after modifying any CMakeLists.txt — run the generation script from the root of the project: 

# Run once before your first build
generate-cmake-project.bat
ℹ️ This script invokes CMake with the correct MinGW Makefiles generator and writes the build tree into the build/ directory. You do not need to re-run it on every compilation — only when the CMake configuration changes.

4 — Build

Once the project has been generated, compile from the root of the project:

build.bat

This invokes cmake --build on the pre-generated tree. Output binaries (hrldll.dll, import libraries and test executables) are placed in build/bin/.

✅ A clean full build workflow always follows the same order: generate-cmake-project.bat → build.bat. For incremental builds, build.bat alone is sufficient.

Initialization RHI

The three initialization functions must be called in strict order during engine startup. They set up the graphics API loader, allocate GPU-side resources that depend on the swapchain dimensions, and register the global backend state used by all subsequent RHI calls.

void RHI_Init()

Initializes global backend state and loads the graphics API. This is the very first RHI call made by the engine. At this stage, no window or GPU context exists yet — the function only prepares internal tables, default values and any pre-context state the backend requires (e.g. function-pointer stubs, debug layer toggles).

ℹ️ Do not issue any OpenGL calls inside RHI_Init. The context is not yet current. GPU resource allocation belongs in RHI_InitContext.
void RHI_InitContext( HRL_uint width, HRL_uint height, void* loader)

Initializes the rendering context and all swapchain-dependent resources. Called immediately after the platform window and its OpenGL context have been created by GLFW. This is where the backend should load API function pointers via the provided loader (e.g. glfwGetProcAddress), compile default shader programs, create shared VAOs/VBOs for the debug renderer, allocate the color-picking framebuffer, and set the initial viewport.

ParameterTypeDescription
widthHRL_uintInitial framebuffer width in pixels
heightHRL_uintInitial framebuffer height in pixels
loadervoid*Platform proc-address loader (cast from GLADloadproc)
void RHI_Shutdown()

Releases all backend-owned GPU objects and shuts down the graphics API. Must be called before the GLFW window is destroyed. This includes deleting every shader program, VAO, VBO, texture, and framebuffer created during the lifetime of the backend. Failure to release resources before context destruction results in driver-side leaks and may cause crashes on subsequent launches in debug drivers.

Frame Flow Frame

HRL follows a deterministic per-frame order. The backend must correctly implement the two frame-boundary functions so the engine can safely issue draw calls between them. The expected call sequence per frame is: 

// Engine-side frame loop (simplified)
RHI_BeginFrame();
RHI_BindViewport(&viewport);
RHI_ComputeFrameMatrices();
RHI_UpdateLights(lights);
// ... scene draw calls ...
RHI_DrawDebug(...);
RHI_ResetFramebuffer();
// ImGui render pass follows
void RHI_BeginFrame()

Marks the beginning of a new GPU frame. The backend should clear per-frame counters (draw calls, triangle count), reset any transient state from the previous frame, and prepare the debug renderer's CPU-side primitive buffers for re-filling. Does not clear the framebuffer — scene clearing is the responsibility of RHI_ClearScene.

void RHI_ResetFramebuffer()

Resets framebuffer bindings to the default backbuffer (GL_FRAMEBUFFER target 0). Must be called after all scene passes and before the ImGui render pass, which expects to draw directly to the default framebuffer. Failure to call this will cause ImGui to render into the scene FBO instead of the screen.

Viewport & Camera View

Viewport binding and matrix computation are separated so the backend can cache camera-derived matrices for the full duration of a frame without recomputing them per draw call.

void RHI_BindViewport( HRL_Viewport* viewport)

Stores a pointer to the active viewport descriptor and calls glViewport with its dimensions. The viewport struct carries the attached camera's position, orientation, field of view and near/far clip planes. Must be called at least once per frame before any draw calls are issued. Calling it mid-frame is valid and switches the active camera for subsequent draws.

ParameterTypeDescription
viewportHRL_Viewport*Non-null pointer to a valid viewport descriptor. Lifetime must exceed the frame.
void RHI_ComputeFrameMatrices()

Computes and caches the view and projection matrices from the currently bound viewport. The resulting matrices are stored internally and exposed via RHI_GetViewMatrix / RHI_GetProjectionMatrix. Must be called after RHI_BindViewport and before the first RHI_BindMaterial of the frame, as materials consume these matrices when uploading shader uniforms.

Materials & Draw Draw

The draw pipeline is split into two steps: binding a material (shaders + textures + GPU state) and submitting a mesh. This separation allows the engine to batch multiple meshes that share the same material without redundant state changes.

void RHI_BindMaterial( HRL_Material* material)

Activates a material for subsequent draw calls. The backend must bind the material's shader program, upload per-material uniforms (model matrix, light array, camera position), and bind all textures declared in the material's textureParams_ map to their respective texture units. Texture slots must be iterated with deterministic ordering — use an ordered_map or explicit slot indices to avoid binding order non-determinism.

⚠️ Never use operator[] on the internal texture map during binding. It silently inserts a default-constructed entry for missing keys, which leaves a texture slot unbound and produces rendering artifacts.

For each texture channel (albedo, normal, roughness, …), fall back to the channel's registered fallback texture if the material does not declare that slot. Fallback textures must be created during RHI_InitContext.

void RHI_DrawMesh( HRL_Mesh* mesh)

Binds the mesh's VAO and issues the GPU draw call. The mesh is expected to carry a pre-uploaded VBO and EBO with positions, normals, UVs and tangents interleaved. The backend uploads the per-object model matrix uniform before issuing glDrawElements. A material must have been bound via RHI_BindMaterial before calling this function.

Lights Lighting

void RHI_UpdateLights(HRL_LightArray lights)

Uploads the scene's light data to the backend's internal light buffer for the current frame. This data is then consumed by RHI_BindMaterial when uploading lighting uniforms to each shader. Must be called once per frame before any draw calls. Light components must be initialized to HRL_INVALID_ID and must guard against issuing RHI callbacks before their Init() has completed — calling RHI_UpdateLights with a partially constructed light entry results in undefined uniform data.

Window Platform

void RHI_WindowResizeCallback( int width, int height)

Handles a framebuffer resize event forwarded from the GLFW resize callback. The backend must call glViewport(0, 0, width, height), resize all scene framebuffer texture attachments via RHI_ResizeSceneTexture, and recompute projection matrices on the next call to RHI_ComputeFrameMatrices. The color-picking framebuffer must also be resized to match the new dimensions.

ParameterTypeDescription
widthintNew framebuffer width in pixels (may be 0 on minimize)
heightintNew framebuffer height in pixels (may be 0 on minimize)
ℹ️ Guard against zero dimensions. When the window is minimized, width and height may both be 0. Skip all resize operations in this case to avoid framebuffer completeness errors.

Textures Resources

All texture objects are owned by the backend and referenced externally via opaque HRL_id handles. The caller never holds a raw pointer to GPU resources. Every texture created with RHI_CreateTexture or RHI_CreateTextureFromBitmap must eventually be freed with RHI_DeleteTexture.

HRL_id RHI_CreateTexture(const char* path, ...)

Loads an image file from disk, uploads it to the GPU, and returns an opaque HRL_id handle. The backend is responsible for flipping the image vertically on load (OpenGL UV origin is bottom-left), generating mipmaps, and applying the default min/mag filters. Returns HRL_INVALID_ID on failure.

HRL_id RHI_CreateTextureFromBitmap(unsigned char* data, int w, int h, int channels)

Creates a texture directly from a raw pixel buffer in CPU memory. Used for procedural textures, fallback textures created at startup, and ImGui font atlases. The backend does not take ownership of data — the caller may free the buffer immediately after this call returns.

void RHI_DeleteTexture(HRL_id id)

Frees the GPU texture object associated with id and removes it from the backend's internal registry. Passing HRL_INVALID_ID is a no-op. Passing a handle that was already deleted is undefined behaviour.

void RHI_GetTextureSize(HRL_id id, int* w, int* h)

Returns the pixel dimensions of the texture. The backend should cache these at creation time rather than querying the GPU.

void RHI_SetTextureMinFilter(HRL_id id, HRL_FilterMode mode)

Sets the minification filter (GL_TEXTURE_MIN_FILTER) for the given texture. The texture must be bound before calling glTexParameteri.

void RHI_SetTextureMaxFilter(HRL_id id, HRL_FilterMode mode)

Sets the magnification filter (GL_TEXTURE_MAG_FILTER) for the given texture. Valid values are HRL_FILTER_NEAREST and HRL_FILTER_LINEAR — mipmap modes are not valid for magnification.

Scenes Framebuffer

In HRL, a Scene is a framebuffer wrapper. Each scene owns a color attachment texture (rendered into by the main pass), an optional depth-stencil renderbuffer, and optionally a second color attachment used by the color-picking pass. The scene texture is then sampled by the editor's ImGui viewport panel.

void RHI_CreateScene(HRL_id* out, HRL_uint width, HRL_uint height)

Allocates a framebuffer object and its color attachment texture at the specified dimensions. Writes the new scene handle into *out. Also creates a depth-stencil renderbuffer for correct depth testing. The scene must be resizable via RHI_ResizeSceneTexture.

void RHI_DeleteScene(HRL_id id)

Destroys the framebuffer object, its color texture and depth renderbuffer associated with id. If the color-picking buffer was enabled on this scene it must also be freed here.

void RHI_BindScene(HRL_id id)

Binds the scene's framebuffer as the active render target. All subsequent draw calls write into the scene's color and depth attachments until RHI_ResetFramebuffer is called.

void RHI_ClearScene()

Clears the currently bound scene's color and depth buffers. Must be called at the start of each frame after RHI_BindScene. If the color-picking attachment is active on the bound scene, it must also be cleared here (to a sentinel value such as black — actor ID 0 is reserved as "no selection").

void RHI_ResizeSceneTexture(HRL_id id, HRL_uint width, HRL_uint height)

Resizes the scene's color attachment and depth renderbuffer to the new dimensions. This must re-allocate the texture storage (via glTexImage2D with NULL data) and the renderbuffer storage (via glRenderbufferStorage), then re-attach them to the FBO. The framebuffer completeness must be verified after resizing.

void RHI_EnableColorPickingBuffer(HRL_id scene)

Attaches a second GL_RGB color attachment to the scene's FBO dedicated to the editor color-picking pass. Each actor is rendered into this attachment with a flat shader encoding its unique 24-bit ID as an RGB value. The editor then calls glReadPixels at the cursor position (with a Y-axis flip, since OpenGL origin is bottom-left) and decodes the ID from the returned pixel. Enable this buffer only for editor-mode scenes to avoid the GPU memory cost in game mode.

ℹ️ The second attachment must be declared with GL_COLOR_ATTACHMENT1 and selected via glDrawBuffers. Do not use GL_COLOR_ATTACHMENT0 for the picking pass or the main render output will be overwritten.

Shaders Resources

Shaders are compiled and linked entirely inside the backend. The HRL core has no knowledge of GLSL. Shader sources are embedded in the backend or loaded from disk relative to the DLL at startup. The backend exposes shader handles as HRL_id values that materials reference by ID.

Expected default shaders

ShaderPurpose
litStandard Blinn-Phong lit material with albedo, normal and roughness slots
unlitFlat color / texture pass-through, no lighting
pickingEncodes actor ID as RGB into the color-picking attachment
debugImmediate-mode colored lines and triangles for the debug renderer

Matrices Math

The backend computes and owns the three per-frame transform matrices. They are uploaded to shader uniforms by RHI_BindMaterial and can be queried externally for debug or editor purposes. All matrices use column-major storage (GLM default) compatible with glUniformMatrix4fv.

void RHI_GetProjectionMatrix(HRL_mat4* out)

Writes the current perspective projection matrix into *out. Computed from the bound viewport's field of view, aspect ratio and clip planes using glm::perspective. Valid only after RHI_ComputeFrameMatrices has been called this frame.

void RHI_GetViewMatrix(HRL_mat4* out)

Writes the current view matrix into *out. Derived from the camera's world-space position and forward vector using glm::lookAt.

void RHI_GetModelMatrix(const HRL_Transform& transform, HRL_mat4* out)

Computes and writes the model matrix for the given transform (position, rotation, scale) into *out. The backend builds the matrix as T * R * S (translate, then rotate, then scale). Called by RHI_DrawMesh internally before uploading the model uniform.

Debug Tools

The debug renderer is an immediate-mode overlay that draws colored lines and filled triangles each frame without persistent scene objects. All primitives submitted during a frame are flushed in a single draw call at the end of the frame.

void RHI_DrawDebug(const HRL_DebugBatch& batch)

Uploads the frame's accumulated debug primitives to the shared VBO and issues the draw call. Lines and filled triangles are drawn as separate GL_LINES and GL_TRIANGLES passes using the debug shader. Depth testing should be disabled for debug overlays so they are always visible above scene geometry. Must be called after the main scene pass and before RHI_ResetFramebuffer.

The debug batch is populated by the physics world's b2DebugDraw callbacks each frame. The RHI implementation must not retain the batch pointer beyond this call.
